# Existing chat UI options

Research date: 2026-09-08. Planning only; no installation or runtime verification. Scope: Open WebUI and Chainlit as interfaces for the application's own shopping assistant. Assessment assumes the existing Python 3.14/FastHTML application, SQLite authority, local Ollama, and working systemd/Tailscale deployment described in the task.

## Recommendation

Both can save chat-interface work. Open WebUI is the stronger choice for a complete, separate household Ollama chat application. Chainlit is the more natural interface for application-written Python agent logic. Neither is currently a drop-in dependency for this Python 3.14 application: Open WebUI documents Python 3.11/3.12 support, and Chainlit's current main package metadata explicitly excludes 3.14. Keeping either in a separate supported-runtime service is the practical integration assumption; this introduces deployment and protocol work that an existing FastHTML chat page would avoid. This is an architectural inference, not a tested integration. [Open WebUI Python environments](https://docs.openwebui.com/getting-started/quick-start/install-methods/python-environments/), [Chainlit package metadata](https://raw.githubusercontent.com/Chainlit/chainlit/main/backend/pyproject.toml).

## Open WebUI

- Ready-made self-hosted chat application with native Ollama and OpenAI-compatible provider connections. It can run using Python/uv without Docker; the docs recommend Python 3.11 for production. Pin an evaluated release rather than reproducing the docs' `@latest` example in deployment. [Overview](https://docs.openwebui.com/), [Python installation](https://docs.openwebui.com/getting-started/quick-start/install-methods/python-environments/).
- Two distinct integration choices: expose narrow application-owned read tools through OpenAPI and let Open WebUI drive the model/tool loop; or use a thin Pipe Function to proxy an application-owned assistant. Pipe Functions can represent custom agents as selectable models. The second option better preserves agent behavior across a future Telegram interface, but requires an adapter. This preference is an inference. [OpenAPI tools](https://docs.openwebui.com/features/extensibility/plugin/tools/openapi-servers/), [Functions](https://docs.openwebui.com/features/extensibility/plugin/functions/).
- Tool execution and evidence can be visible. Native plugins support status and citation events; external tools can post events back to a chat/message endpoint when forwarding headers are enabled. Citation metadata can carry application evidence URLs. A self-contained agent must avoid emitting `delta.tool_calls` for tools it already executed, because that triggers the UI's tool-execution loop; the docs describe display blocks for completed tool calls. [Events](https://docs.openwebui.com/features/extensibility/plugin/development/events/), [Pipe integration caveat](https://docs.openwebui.com/features/extensibility/plugin/functions/pipe/).
- It owns a separate SQLite `webui.db` for chat history/configuration. Keep that database separate from shopping facts and application migrations; read tools should query the shopping application's APIs. The separation recommendation follows the repository's persistence invariants. [Database export documentation](https://docs.openwebui.com/tutorials/maintenance/database/).
- Do not choose the old Pipelines service for new work: current docs mark it legacy and recommend Functions, Tools, or external tool servers. [Pipelines status](https://docs.openwebui.com/features/extensibility/pipelines/).
- The current license includes branding restrictions with an exception for at most 50 end users in any rolling 30-day period, so the household scenario fits that exception. Check the pinned version's license if redistributing. [License text](https://github.com/open-webui/open-webui/blob/main/LICENSE).

## Chainlit

- Supplies a complete web chat with streaming, elements, feedback, and optional history. `@cl.on_message` invokes ordinary application-written Python, so an adapter can call the shopping assistant without adding LangChain. Ollama connectivity can use its OpenAI-compatible API; combining these documented interfaces is an integration inference, not a verified Chainlit/Ollama example. [Web UI](https://docs.chainlit.io/deploy/webapp), [Pure Python](https://docs.chainlit.io/get-started/pure-python), [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility).
- Steps display tool inputs/outputs and can be collapsed; text elements support Markdown and inline/side/page display. The adapter can display returned evidence excerpts and application links, while retaining provenance decisions in application code. [Steps](https://docs.chainlit.io/api-reference/step-decorator), [Text elements](https://docs.chainlit.io/api-reference/elements/text).
- Chats are not persisted by default. The official persistence layer uses PostgreSQL, and the community SQLAlchemy layer is documented as tested with PostgreSQL, not as a ready SQLite solution. A custom data layer is supported but requires implementing user/thread/step/element/feedback operations. For SQLite-only operation, this is real additional work; an initial nonpersistent chat avoids it. [Persistence default](https://docs.chainlit.io/data-persistence/overview), [Layer options](https://docs.chainlit.io/data-layers/overview), [SQLAlchemy layer](https://docs.chainlit.io/data-layers/sqlalchemy), [Custom layer API](https://docs.chainlit.io/api-reference/data-persistence/custom-data-layer).
- `chainlit run` serves the UI without requiring Docker. FastAPI subapplication mounting is documented, but it does not establish compatibility with this FastHTML application. More decisively, current main declares `>=3.10,<3.14.0`; a separate supported-runtime UI process calling the application backend is the likely path while retaining the project's Python 3.14 requirement. [Running Python apps](https://docs.chainlit.io/get-started/pure-python), [FastAPI mounting](https://docs.chainlit.io/integrations/fastapi), [Package metadata](https://raw.githubusercontent.com/Chainlit/chainlit/main/backend/pyproject.toml).
- Apache-2.0 licensed. The repository also says it has been community-maintained since May 2025; evaluate release maintenance when choosing it. [Official repository](https://github.com/Chainlit/chainlit).

## Decision boundary

Use Open WebUI if a separate, mature general chat destination is desirable. Consider Chainlit if a separate Python-controlled conversational application is desirable and its persistence/runtime work is acceptable. For one chat surface tightly integrated with existing shopping order views, neither removes the need to implement the deterministic read tools, bounded agent loop, exact-money handling, provenance, and SQLite ownership; those remain application responsibilities. A small existing-stack interface may therefore be less total work even though it provides fewer chat features initially.
